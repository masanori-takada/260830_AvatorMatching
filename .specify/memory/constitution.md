# AIアバター自動マッチング Constitution

## Core Principles

### I. 匿名性と段階的開示を設計の中心に置く

匿名性は追加機能ではなく、すべての仕様・データモデル・API・画面遷移の前提とする。
利用者ごとのデータ分離をデータベース層で強制し、相互承諾が成立するまで名前・所属その他の
識別情報をクライアントへ返してはならない。管理権限をブラウザへ渡してはならず、権限分離と
開示境界は自動テストで検証しなければならない。初期版では実名、メールアドレス、電話番号を
収集しない。

### II. 動く縦切りを優先する

各マイルストーンは、利用者が開始から価値到達点まで操作できる独立した縦切りとして完成させる。
初期版は匿名開始、20問のインタビュー、デモ候補とのアバター会話、相性レポート、承諾または
辞退、承諾後の架空プロフィール開示までを一気通貫で提供する。正式認証、実ユーザー探索、
企業管理、高度な運営機能は、この縦切りが検証された後に追加する。将来機能のためだけの抽象化や
基盤を先行実装してはならない。

### III. テスト可能な契約を先に定める

状態遷移、データ所有権、開示条件、AI出力形式、失敗時の復旧動作は、実装前に検証可能な契約として
定義しなければならない。機能追加と不具合修正は、単体、統合、データベース権限、E2Eのうち
リスクに対応する自動テストを伴う。特に他利用者データの遮断と承諾前情報漏洩ゼロは、実装完了の
必須ゲートとする。型検査、Lint、テスト、プロダクションビルドが成功するまで完了扱いにしない。

### IV. 既存デモの体験を忠実に継承する

既存のHTML/CSS/JavaScript、ホーム画像、GIF、事業資料をUIと体験の基準資料とする。配色、文言の
温度感、カード構成、スマートフォン中心の表示、主要画面遷移を維持し、現在必要な操作だけを
明確に強調する。Reactへの再構築を理由に無関係な再デザインを行ってはならない。キーボード操作、
可視フォーカス、十分なコントラスト、動きを減らす設定、狭い画面での可読性を必須品質とする。

### V. 外部連携を交換可能かつ観測可能にする

AI生成、永続化、認証などの外部機能は、画面やドメインロジックから明確な境界で分離する。
AI処理は共通契約の下でモック実装とAmazon Bedrock実装を交換可能にし、処理状態を
`queued`、`processing`、`completed`、`failed` として記録する。外部障害は利用者の入力を失わせず、
再試行可能な状態へ収束させる。構造化ログには処理識別子と失敗分類を含め、秘密情報、個人情報、
回答全文を記録してはならない。

## 技術・セキュリティ制約

- WebアプリはNext.js App RouterとTypeScriptで構築し、永続化、匿名セッション、Realtime、Storageは
  Supabaseを利用する。
- すべての利用者所有テーブルでRow Level Securityを有効化し、所有者IDに基づくポリシーを設ける。
- AWS Bedrockは東京リージョンを基本とし、サーバー側からのみ呼び出す。出力トークン上限を明示し、
  IAM権限を必要最小限に限定する。
- 初期版のAIプロバイダーはモックを標準とし、設定不備による本番環境での黙示的フォールバックを
  禁止する。
- 秘密値は環境変数または適切な秘密管理へ置き、リポジトリ、クライアントバンドル、ログへ含めない。
- データベース変更は再現可能なマイグレーションとして管理し、手作業だけのスキーマ変更を禁止する。

## 開発ワークフローと品質ゲート

1. 事業資料、既存デモ、承認済み仕様を単一の要求根拠として確認する。
2. Spec Kitで仕様、計画、タスクを作成し、仕様と計画はGPT-5.6 solで作成・レビューする。
3. 実装はGPT-5.6 Terraで進め、各タスクで関連テストを追加して検証する。
4. 実装完了後はGPT-5.6 solで仕様適合性、セキュリティ、回帰、保守性をレビューする。
5. 指摘修正後に、型検査、Lint、自動テスト、E2E、ビルド、主要画面のスクリーンショット比較を
   再実行する。
6. 既存の未コミット変更と無関係なファイルを保持し、コミットは意図した成果物だけに限定する。

仕様変更が匿名性、開示条件、主要フロー、データ所有権へ影響する場合は、実装前に仕様承認を
取り直さなければならない。複雑さを追加する場合は、解決する具体的な要件と、より単純な代替案を
採用できない理由を計画へ記録する。

## Governance

本憲章はプロジェクト内の他の開発慣行より優先する。改定には、変更理由、影響する仕様・計画・
テスト、必要な移行手順を記録し、利用者の承認を得なければならない。バージョンはセマンティック
バージョニングに従い、原則の削除または互換性のない再定義をMAJOR、新原則または実質的な拡張を
MINOR、意味を変えない明確化をPATCHとする。

仕様、計画、コードレビューでは本憲章への適合を明示的に確認する。違反を例外として認める場合は、
範囲、期限、リスク、解消条件を同じ成果物に記録する。各リリース前に、匿名性、RLS、段階的開示、
復旧可能性、テスト結果、既存デモとの視覚的一貫性を再確認する。

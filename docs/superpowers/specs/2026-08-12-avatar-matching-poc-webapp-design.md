# AIアバター自動マッチング PoCデモアプリ 設計書

- 作成日: 2026-08-12
- 対象: PoC / 展示会デモ用 iOSアプリ風Webモック
- ステータス: 実装着手可(この設計書をもとに実装計画を作成する)

---

## 1. 概要 / 背景

### 1.1 事業コンセプト

「AIアバター自動マッチング」は、刈谷エリアの参加企業の従業員に対し、福利厚生として無償提供される出会い支援サービスである。

最大の特徴は、**ユーザー本人が相手と直接やり取りしない**点にある。本人のAIアバターが裏側で相手候補のAIアバターと自律的に会話し、相性が確認できたペアにのみ通知が届く。ユーザーは「探す」「申し込む」「断られる」という従来のマッチングアプリ特有の消耗から解放される。

体験フローは以下の6ステップ。

1. 招待コードで登録
2. 設問にAIインタビュー形式で回答
3. 本人が寝ている間にアバターが裏で会話
4. 相性が高い時だけ通知が届く
5. 会話ログと相性レポートを読んで承諾/辞退を判断
6. 両者OKで実名・所属・面談候補日時が開示される

**匿名性はこのサービスの前提条件である。** 実名・所属はアプリのどこにも表示されず、両者が承諾した後にのみ開示される。人事も運営者も個人のマッチ内容を閲覧できない設計とする。この思想は、デモアプリにおいても画面上の表現として一貫して反映する。

相性レポートは以下の5軸で構成する。

| 軸 | 内容 |
|---|---|
| 会話の弾み | やり取りのテンポ、話題の広がり |
| 価値観の一致 | 生活・仕事・将来観の重なり |
| ユーモアの相性 | 笑いのツボ、軽口の受け止め方 |
| 相互関心 | 互いへの質問量・掘り下げの深さ |
| 不一致の重大度 | 相違点が関係にとって致命的か(低いほど良い) |

### 1.2 PoCの位置づけ

事業側の仕様設計は完了しており、ロードマップ上の次フェーズが「PoC実装」である。本PoCのゴールは、**登録からマッチ成立までを一気通貫で操作でき、会場で3分間のデモとして見せられるアプリ**を用意すること。

ビジネス上の目的は、参加企業・関係者に対して「AIが代わりに会っている」という体験の手触りを伝え、事業への合意形成を進めることにある。したがって本PoCは技術検証ではなく **体験の可視化** を目的とする。実際のLLM推論・マッチングアルゴリズム・サーバーインフラはスコープ外とする。

## 2. スコープ

### 2.1 やること

- 登録 → AIインタビュー → アバター会話 → マッチ通知 → 相性レポート → 実名開示、という一連の体験フローを**実際にクリックで操作できる**アプリを作る
- 全画面を iPhone実機を模した枠(幅375px程度、ステータスバー・下部タブバーを含む)の中で完結させ、ブラウザ上で「iOSアプリを操作している」体験にする
- GitHub Pages にそのままデプロイできる、**プレーンHTML/CSS/JS(依存ライブラリなし、ビルド不要)** で実装する
- 提供されたホーム画面イメージのトンマナを全画面で統一する
- 会話ログ・相性スコア・実名開示後プロフィールは、固定のダミーデータとして `app.js` 内にハードコードする
- 進行状態を `localStorage` に保存し、リロードしても直前のステップから再開できるようにする
- 展示会で何度もデモを回せるよう、「デモをリセット」機能を用意する

### 2.2 やらないこと

- 実サーバー、API、データベースの構築(**外部通信は一切行わない**)
- 実際のLLM API呼び出し(会話ログは事前に用意した固定サンプル)
- 実際のマッチングアルゴリズム(相性スコアは固定値)
- ユーザー認証、招待コードの検証(空欄チェックのみ)
- プッシュ通知(アプリ内の演出として表現する)
- 複数の相手候補との同時マッチング(固定NPC 1人のみ)
- レスポンシブ対応(PC/スマホのブラウザ両方で「375px枠」が中央に表示されればよい)
- 自動テスト(静的サイト+PoCのため。手動QAチェックリストで代替する)
- GitHubへのpush、GitHub Pagesの有効化(手順を Next Steps に記載し、ユーザー自身が実施)
- 多言語対応(日本語のみ)
- アクセシビリティの網羅的対応(ただし後述の最低限は満たす)

## 3. アーキテクチャ

### 3.1 ファイル構成

リポジトリルート直下に配置する。GitHub Pages のルート公開でそのまま動く形にする。

```
/
├── index.html                     … 全画面のマークアップを内包するSPA
├── style.css                      … 全スタイル
├── app.js                         … 状態管理・画面遷移・固定データ
├── assets/
│   └── hero.png                   … ヒーロー画像(提供イメージから切り出し。無い場合はCSSグラデーションで代替)
├── docs/
│   └── superpowers/specs/         … 本設計書
├── AIアバター自動マッチング_事業概要.pdf
└── ホームイメージ画像.png
```

- 依存ライブラリ・ビルドツール・パッケージマネージャは**一切使わない**。`index.html` をダブルクリックすればローカルでも動く
- アイコンは外部フォントを使わず、**インラインSVG**(線画風、`stroke` ベース)で実装する。`index.html` 内の `<svg><symbol>` スプライトにまとめ、`<use>` で参照する
- 画像アセットは `assets/hero.png` のみ許容する。用意できない場合はCSSグラデーション+SVGで代替してよく、**画像が無くてもアプリは成立する**こと

### 3.2 SPA構造

単一ページ内に全画面を配置し、JavaScriptで表示を切り替える。

```html
<div class="phone">              <!-- 375px幅の端末枠 -->
  <div class="status-bar">…</div>
  <main class="viewport">
    <section class="screen" data-screen="invite">…</section>
    <section class="screen" data-screen="interview">…</section>
    <section class="screen" data-screen="waiting">…</section>
    <!-- 以下同様 -->
  </main>
  <nav class="tab-bar">…</nav>
</div>
```

- `.screen` はデフォルト `display: none`。`is-active` クラスが付いたものだけ表示する
- 画面遷移は `showScreen(name)` 関数に一本化する。この関数は以下を行う
  1. 全 `.screen` から `is-active` を除去し、対象に付与
  2. `state.currentScreen` を更新して `saveState()`
  3. `viewport` のスクロール位置を先頭に戻す
  4. 画面ごとの再描画フック `renderers[name]?.()` を呼ぶ
  5. 下部タブバーの表示/非表示とアクティブ状態を更新
- 画面ごとの描画ロジックは `renderers` オブジェクトに `画面名: 関数` の形で登録する。DOM生成はテンプレートリテラル+`innerHTML` でよい(固定データのみを扱うため)
- グローバル汚染を避けるため、`app.js` 全体を IIFE で包む。デモ運用の都合上、`window.__demo = { reset, showScreen, state }` のみ公開する(展示会での緊急操作用)

### 3.3 状態管理と永続化

- アプリ状態は単一の JavaScript オブジェクト `state` に集約する
- 変更時は必ず `saveState()` を呼び、`localStorage` のキー `avatarMatchingDemo.v1` に JSON で保存する
- 起動時に `loadState()` で復元する。復元処理は以下の防御を行う
  - キーが存在しない → 初期状態で開始
  - JSON パースに失敗 → 破損とみなし、`localStorage` を消去して初期状態で開始(**例外を投げてデモを止めない**)
  - 保存データの `version` が現行と異なる → 初期状態で開始
- 復元後は `state.currentScreen` の画面を表示する。ただし `waiting` 画面で保存されていた場合は、待機タイマーを再開する(後述)
- **外部送信は一切行わない。** `fetch` / `XMLHttpRequest` / `<form action>` を使用しない。この点はプライバシー説明画面の記述と整合させる

## 4. 画面一覧と各画面の仕様

### 画面マップ

```
[1] 招待コード入力 ─登録する→ [2] AIインタビュー ─全問回答→ [3] アバター会話中(待機)
                                                                    │ 数秒後 自動
                                                                    ↓
[6] 実名開示 ←会うを選択─ [5] 会話ログ・相性レポート ←カードtap─ [4] お知らせ一覧
                                                                    ↑
                                       [H] ホーム ←────────────────┘
                                        │
                                        ├→ [P] プライバシー説明
                                        ├→ [F] よくある質問
                                        ├→ [S] 設定(デモをリセット)
                                        ├→ [M] マイページ
                                        └→ [R] プロフィール
```

下部タブバー(ホーム/マイページ/メッセージ/プロフィール)は、**登録完了後(画面3以降)のみ表示**する。画面1・2では非表示とし、オンボーディングの一本道感を出す。

---

### [1] 招待コード入力画面 (`invite`)

**遷移条件:** アプリ初回起動時、および「デモをリセット」実行後の初期画面。

**表示内容:**
- サービスロゴ(重なった2つの円の線画SVG)+ サービス名「AIアバター自動マッチング」
- キャッチコピー「AIが代わりに会っている。」
- 説明文: 「勤務先から配布された招待コードを入力してください。実名や所属は、相手とお互いがOKするまで誰にも表示されません。」
- 招待コード入力欄(`<input type="text">`、プレースホルダ `例: KARIYA-2026`)
- 主ボタン「登録する」
- 補足テキスト: 「※本アプリはデモ用です。入力内容はお使いの端末内にのみ保存され、外部には送信されません。」

**操作:**
- 「登録する」タップ時
  - 入力値が空白のみ → 入力欄下にエラー文「招待コードを入力してください」を赤系で表示し、遷移しない。入力欄に `is-error` クラスを付与
  - それ以外 → **どんな文字列でも通す**。`state.inviteCode` に保存、`state.registered = true` にして `interview` へ遷移
- 一度でも入力があればエラー表示は消える(`input` イベントで解除)

---

### [2] AIインタビュー画面 (`interview`)

**遷移条件:** 招待コード登録の完了後。

**表示内容:**
- ヘッダー: 「AIインタビュー」+ 進捗インジケーター「3 / 6」+ 進捗バー
- チャット風UI。AI(アバター)の吹き出しは左寄せ・淡いピンク背景、ユーザーの回答は右寄せ・ワインレッド系背景で表示する
- 冒頭にAIからの導入メッセージ:「はじめまして。あなたのAIアバターです。これから6つだけ質問させてください。あなたの答え方や考え方を学んで、私があなたの代わりに相手と話します。」
- 回答済みの質問と回答は画面上に履歴として積み上がる。新しい質問が出るたび最下部へスクロールする

**設問(全6問。選択式4問+自由記述2問):**

| # | 種別 | 設問文 | 選択肢 |
|---|---|---|---|
| 1 | 選択 | 休日の過ごし方に近いのはどちらですか? | 外に出かけて人と会う / 家でゆっくり自分の時間 / 日によって半々くらい |
| 2 | 選択 | 初対面の人と話すとき、あなたは? | 自分から話しかける方 / 相手が話すのを聞く方 / 場の空気を見て決める |
| 3 | 自由記述 | 最近、思わず時間を忘れて夢中になったことは何ですか? | (テキスト入力) |
| 4 | 選択 | 一緒にいて心地よいと感じるのは、どんな人ですか? | 笑いのツボが合う人 / 価値観や考え方が近い人 / 自分にない視点をくれる人 |
| 5 | 選択 | 将来について、今の気持ちに近いのは? | 具体的に考えている / なんとなく考えている / まだこれから考えたい |
| 6 | 自由記述 | 相手に、これだけは知っておいてほしいことはありますか? | (テキスト入力) |

**操作:**
- 選択式: 選択肢がボタンとして並ぶ。タップすると、その選択肢がユーザーの吹き出しとして履歴に追加され、約600ms後に次の質問がAIの吹き出しとして表示される(タイピング演出として「…」を表示する)
- 自由記述: 画面下部にテキスト入力欄+送信ボタンが表示される。**空欄では送信できない**(送信ボタンを `disabled` にする)
- 全6問回答後、AIから締めのメッセージ「ありがとうございます。あなたのことが分かってきました。あとは私にまかせて、ゆっくり休んでください。」を表示し、その下に「アバターにまかせる」ボタンを表示。タップで `state.interviewDone = true` にして `waiting` へ遷移
- 回答は都度 `state.answers[]` に `{ id, question, answer, type }` の形で保存する。途中でリロードしても続きから再開できる
- **戻る操作は提供しない**(オンボーディング中の分岐を減らし、デモの流れを単純に保つため)

---

### [3] アバター会話中(待機)画面 (`waiting`)

**遷移条件:** インタビュー完了後。またはホームの「現在の状況」カードから。

デモの山場となる画面。ホーム画面イメージのデザインを踏襲する。

**表示内容:**
- ヒーローカード: 「AIが代わりに会っている。」+ 説明文「あなたのAIアバターが相手のアバターと会話し、相性を確かめています。」
- 「現在の状況」カード: 「アバターが会話中です」/「あなたのアバターが、複数の候補アバターと会話を進めています。」+ 微細なパルスアニメーション(アバターアイコンが淡く明滅する)
- **ステップインジケーター**(5段階、横並び、円形アイコン+ラベル、間は点線で接続)
  1. 登録完了(完了)
  2. インタビュー完了(完了)
  3. アバターが会話中(**現在** — 塗りつぶし+濃いワインレッド、ラベルも同色)
  4. 相性が高い時に通知(未達 — グレー)
  5. 会話ログを読んで判断(未達 — グレー)
- 補足文: 「相性の基準を満たしたときだけ通知が届きます。基準に満たない場合は、何も起きません。」

**操作 / 演出:**
- この画面に入ってから **6秒後** に、マッチ通知が自動的に発生する
  - `state.notified = true` にして保存
  - 画面上部にトースト風の通知バナー「新しいマッチ候補がいます」をスライドインさせる(約4秒表示。タップで `report` へ直接遷移)
  - ステップインジケーターの4番目「相性が高い時に通知」を現在ステップに更新
  - ヘッダーのベルアイコンに未読バッジを表示する。数字は未読お知らせ件数(`NOTIFICATIONS` のうち `state.readNotificationIds` に含まれないもの)とし、通知直後は「2」となる
- 通知発生後、画面下部に「お知らせを見る」ボタンを表示。タップで `notifications` へ遷移
- **展示会での事故防止として、画面のどこかを長押し(700ms)すると待機を即座に完了させる**隠しショートカットを実装する。デモ時間が押している場合に使う
- タイマーは `showScreen` で他画面へ移動した場合はクリアする。ただし `state.notified` が既に `true` の場合は、この画面に再訪しても通知演出は再生せず、通知済みの表示状態で描画する

---

### [4] お知らせ一覧画面 (`notifications`)

**遷移条件:** 待機画面の「お知らせを見る」、ホームのお知らせカード「すべて見る」、ヘッダーのベルアイコン、下部タブ「メッセージ」から。

**表示内容:**
- ヘッダー「お知らせ」
- お知らせカードのリスト(アイコン+タイトル+本文+相対時刻+右向きシェブロン)。未読は左肩に小さなドットを表示
  1. 「新しいマッチ候補がいます」/「相性基準を満たしたペアが見つかりました。」/ 2時間前
  2. 「相性レポートが準備できました」/「会話ログと相性レポートを確認できます。」/ 5時間前
- `state.notified` が `false` の場合は、リストの代わりに空状態「まだお知らせはありません。アバターが会話を続けています。」を表示する

**操作:**
- いずれのカードをタップしても `report` へ遷移する(デモの単純化のため両方とも同じ遷移先)
- タップ時に該当お知らせを既読にし、ベルの未読バッジ数を減らす

### [5] 会話ログ・相性レポート画面 (`report`)

**遷移条件:** お知らせカードのタップ、通知バナーのタップ、ホームのメニュー「会話ログ・相性レポート」から。

本PoCで最も情報量が多く、デモの説得力を担う画面。上から順にスクロールして読ませる。

**表示内容(上から):**

1. **相手ヘッダー**
   - アバターアイコン(線画、性別を特定しない意匠)
   - 表示名「お相手 A さん」+ サブテキスト「実名・所属は非表示です」
   - 「相性 82%」のバッジ
   - 注記:「※お互いが『会う』を選ぶまで、実名・所属は表示されません。」

2. **アバター同士の会話ログ**
   - 「あなたのアバター」と「お相手のアバター」の吹き出しが交互に並ぶ(左右に振り分け)
   - 冒頭に「昨夜 2:14 – 2:17 の会話より抜粋」の見出し
   - 9ターン(4往復半)の固定サンプル(§5.2 に全文を定義)
   - 会話ログ全体を淡いカードで囲み、「これは、あなたが寝ている間にAIアバター同士が交わした会話です。」というキャプションを添える

3. **5軸の相性レポート**
   - 各軸につき: ラベル / 0–100 のバーチャート(CSSの `width: %` で描画、ロード時に0からアニメーション) / 数値 / 一行コメント
   - 「不一致の重大度」のみ **低いほど良い** 指標であることを明示する。バーの色をワインレッドではなくグレー系にし、ラベル横に「低いほど良い」の注記を付ける
   - 各軸に**会話ログからの根拠引用**を1つずつ添える(引用符付き、斜体、淡色。§5.2 に定義)

4. **総評**
   - 「価値観と生活リズムの重なりが大きく、会話のテンポも自然でした。相違点はありますが、関係を妨げるほどではありません。」

5. **判断ボタン**
   - 主ボタン「会う」(ワインレッド塗りつぶし)
   - 副ボタン「今回は辞退する」(枠線のみ)
   - ボタン上に注記:「あなたの判断は相手には通知されません。両者が『会う』を選んだ場合のみ、お互いに開示されます。」

**操作:**
- 「会う」→ `state.decision = 'accept'` を保存し、`reveal` へ遷移。遷移時に「お相手も『会う』を選んでいます」という短い演出(0.8秒のローディング表示)を挟んでから開示する
- 「今回は辞退する」→ 確認ダイアログ風のシート(アプリ内実装、`window.confirm` は使わない)で「辞退すると、このお相手の情報は表示されなくなります。よろしいですか?」を確認
  - 確定 → `state.decision = 'decline'` を保存し、`declined` 画面(「辞退しました。相手には通知されません。アバターは引き続き会話を続けます。」+「ホームに戻る」ボタン)を表示
  - **デモ復帰のため、`declined` 画面には「デモ用: もう一度レポートを見る」リンクを置き、`state.decision` を `null` に戻して `report` へ戻れるようにする**
  - キャンセル → シートを閉じる

### [P] プライバシー説明画面 (`privacy`)

## 6. ビジュアルデザイン方針

### 6.1 提供イメージ(ホーム画面)の解釈

提供された `ホームイメージ画像.png` は以下の特徴を持つ。**本設計はこの画像を正とする。**

- 背景は**明るいオフホワイト**であり、ダーク基調ではない。カードは白、画面全体が白〜淡ピンクの明るいトーンで統一されている
- アクセントカラーは**ワインレッド〜プラム系**(ロゴ、現在ステップ、タブのアクティブ状態、「AIが代わりに会っている。」の見出し)
- 補助色として**淡いピンク**(アイコンの円背景、ヒーローのグラデーション、バッジ)が広く使われる。ゴールドは使用されていない
- カードは**大きめの角丸**(16–20px相当)+ ごく薄い影 + 薄いボーダー
- アイコンは絵文字ではなく、**線画風(ストロークベース)** で統一されている。ヒーロー部分のみ3Dイラスト調のキャラクターが配置される
- 情報は「カードの積み重ね」で構成され、セクション間に十分な余白がある

> **設計上の判断:** 事前のブレインストーミングでは「ダーク・ワインレッド〜プラム系の背景、ピンク/ゴールドのアクセント」と整理されていたが、提供画像は明るい背景・ゴールドなしであった。**実装は提供画像に合わせた明るいトーンとする**(画像がユーザーの意図の最も直接的な表現であるため)。ゴールドは使用しない。

### 6.2 カラートークン

`style.css` の `:root` に CSS カスタムプロパティとして定義し、全画面でこれのみを参照する(色のハードコード禁止)。

  --wine-deep:     #8A1F45;  /* 押下・強調 */

  --pink:          #E9A8C3;  /* 補助ピンク(アイコン円、バー) */

### 6.4 端末枠(フレーム)

- `.phone` は `width: 375px; height: 812px;`(iPhone X系相当)。画面中央に配置し、周囲は淡いグレー(`#E8E4E6`)の背景に置く
- 角丸 40px、外側にごく薄い影。上部にステータスバー(左に固定表示の「9:41」、右に電波・Wi-Fi・電池のSVGアイコン)
- 縦スクロールは `.viewport` の内側だけで発生させる(`overflow-y: auto`)。ページ全体はスクロールさせない
- ビューポート高が 812px + 余白に満たない環境では、`.phone` を `transform: scale()` で縮小して収める(`min()` ベースのCSS変数で対応)

### 6.5 コンポーネントスタイル

- **カード:** 白背景、`--radius-card`、`--shadow-card`、`1px solid var(--border)`、内側パディング 16px、カード間マージン 12px
- **主ボタン:** `--wine` 塗り、白文字、高さ 50px、`--radius-btn`、幅100%。押下で `--wine-deep`
- **副ボタン:** 透明背景、`1px solid var(--wine)`、`--wine` 文字
- **アイコン:** 24×24 のインラインSVG、`stroke: currentColor; stroke-width: 1.6; fill: none; stroke-linecap: round`。円形の淡ピンク背景(40×40)の中央に配置するパターンを多用する
- **吹き出し:** 最大幅 78%、角丸 16px(発話者側の1角のみ 6px)。AI/相手側 = `--pink-soft` 背景 + `--text-main`、自分側 = `--wine` 背景 + 白文字
- **ステップインジケーター:** 円 44px。完了 = `--pink` 塗り+白アイコン、現在 = `--wine` 塗り+白アイコン+ラベルも `--wine` の太字、未達 = `#F0ECEE` 塗り+`--text-sub` アイコン。円の間は 1px 点線で接続し、完了区間のみ実線 `--wine`
- **相性バー:** 高さ 8px、`--radius-pill`、トラックは `#F0EAED`。塗りは `--wine` → `--pink` の横グラデーション。ただし `invertedGood` の軸は `--neutral-bar` 単色。画面表示時に `width` を 0 から目標値へ 700ms でトランジションさせる
- **下部タブバー:** 高さ 56px + セーフエリア相当の余白、白背景、上辺に 1px ボーダー。アクティブタブはアイコン・ラベルともに `--wine`、非アクティブは `--text-sub`
- **アニメーション:** すべて 200–700ms、`ease-out` 基調。`prefers-reduced-motion: reduce` の場合はトランジションを無効化する(バーの幅とフェードは最終状態を即座に適用)

### 6.6 最低限のアクセシビリティ

網羅的な対応は行わないが、以下は満たす。

- すべての操作要素は `<button>` / `<a>` / `<input>` を使う(`div` にクリックハンドラを付けない)。キーボードのTab移動とEnter実行が機能すること
- 装飾用SVGには `aria-hidden="true"` を付け、意味を持つアイコンボタンには `aria-label` を付ける
- 本文テキストとその背景のコントラスト比は 4.5:1 以上を確保する(`--text-sub` の使用箇所を目視確認)
- 画面切り替え時、新しい画面の見出しへ `focus()` を移す

## 7. エラーハンドリング / エッジケース

PoCのため最小限とする。**基本方針は「デモの流れを止めない」。**

### 7.1 ブロックする(唯一のバリデーション)

| 箇所 | 条件 | 挙動 |
|---|---|---|
| 招待コード | 空欄または空白のみ | エラー文表示、遷移しない |
| インタビュー自由記述 | 空欄または空白のみ | 送信ボタンを `disabled` にする |
| インタビュー全体 | 未回答の設問がある | 「アバターにまかせる」ボタンを表示しない |
| 面談日時選択 | 未選択 | 「この日時で調整する」を `disabled` にする |

招待コードは**空欄でなければどんな文字列でも通す**。形式チェック・大文字小文字・長さの検証は行わない。

### 7.2 止めずに処理するエッジケース

| ケース | 対応 |
|---|---|
| `localStorage` が使用不可(プライベートモード等) | `try/catch` で握りつぶし、メモリ上の `state` のみで動作する。機能は全て使えるが、リロードで初期化される。ユーザーへの警告表示は行わない |
| 保存データが破損/JSONパース失敗 | キーを削除して初期状態から開始 |
| 保存データの `version` 不一致 | キーを削除して初期状態から開始 |
| `waiting` 画面をリロードした | `state.notified` が `false` なら待機タイマーを再開する。`true` なら通知済み状態で描画 |
| `waiting` の途中で別画面へ移動 | タイマーを `clearTimeout` する。ホーム等から `waiting` に戻ると改めて 6秒でカウントする |
| 進行前の画面へ直接遷移された(タブ操作等) | 各画面の描画時に前提条件を確認し、満たさない場合は空状態を表示する(例外を投げない)。例: 未通知で `report` へ来た場合は「まだレポートはありません」+ホームへ戻るボタン |
| 「辞退」後に再びレポートを見たい | `declined` 画面のデモ用リンクから復帰できる(§4 [5]) |
| 待機の6秒が長い/デモ時間が押している | 待機画面の長押しショートカットで即座に完了させる(§4 [3]) |
| `assets/hero.png` が存在しない | `onerror` で画像要素を隠し、CSSグラデーションのみで表示する。レイアウトは崩さない |
| ブラウザの戻る/進むボタン | **対応しない**(履歴APIは使わない)。戻るはブラウザ自体の離脱となるが、`localStorage` から復帰できるため実害はない |
| 375px より狭いブラウザ幅 | `.phone` を `transform: scale()` で縮小して収める |

### 7.3 想定ブラウザ

展示会での使用端末を想定し、**Chrome / Safari / Edge の最新版**で動作すれば十分とする。IE、および旧バージョンへの対応は行わない。ES2020 構文(オプショナルチェーン、`??`)の使用を許容する。

### 9.2 GitHub Pages へのデプロイ手順(ユーザー実施)

コード一式の作成とローカル配置までが今回のスコープであり、以下はユーザー自身が後で実施する。

1. **GitHubでリポジトリを作成する**
   - GitHub にログインし、右上の「+」→「New repository」
   - リポジトリ名を入力(例: `avatar-matching-poc`)
   - **Public** を選択する(GitHub Free プランの場合、Pages の公開には Public が必要)
   - 「Add a README file」等のチェックはすべて**外す**(既存のローカルリポジトリと衝突するため)
   - 「Create repository」

2. **ローカルリポジトリをpushする**

   作業ディレクトリで以下を実行する(`<ユーザー名>` と `<リポジトリ名>` は置き換える)。

   ```bash
   git remote add origin https://github.com/<ユーザー名>/<リポジトリ名>.git
   git branch -M main
   git push -u origin main
   ```

3. **GitHub Pages を有効化する**
   - リポジトリの「Settings」→ 左メニューの「Pages」
   - 「Build and deployment」の Source を **「Deploy from a branch」** にする
   - Branch を **`main`**、フォルダを **`/ (root)`** にして「Save」
   - 1〜2分待つと、同ページ上部に公開URL `https://<ユーザー名>.github.io/<リポジトリ名>/` が表示される

4. **公開URLで動作確認する**
   - §8.1 の通しフローをブラウザ(できれば展示会で使う端末)で1回実施する
   - スマートフォンで開く場合は、ブラウザの「ホーム画面に追加」を使うとアドレスバーが消え、よりアプリらしく見える

### 9.3 デモ運用上の注意(ユーザー向け)

- デモの前に必ず「設定 → デモをリセット」を実行し、招待コード入力画面から始める
- 待機画面の自動通知は6秒。時間が押している場合は、待機画面を長押しすると即座に通知が届く
- 進行状況はブラウザごとに保存される。別の端末・別のブラウザで開くと初期状態から始まる
- 会場のネットワークが不安定な場合に備え、公開URLを一度開いた後はオフラインでも動く(静的ファイルのみのため)。念のため、事前にリポジトリをローカルにも置いておくとよい

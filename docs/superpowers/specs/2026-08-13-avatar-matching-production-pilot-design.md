# AIアバター自動マッチング 本番基盤パイロット設計書

- 作成日: 2026-08-13
- 対象: 本番実装の第1マイルストーン（刈谷エリア実証パイロット）
- ステータス: ユーザー承認済み・Spec Kit仕様レビュー待ち
- 要求仕様: `specs/001-avatar-matching-pilot/spec.md`

## 1. 目的と設計方針

既存の静的PoCを、実データ保存と将来拡張が可能なWebアプリへ再構築する。第1マイルストーンでは、
動作が目に見えることを優先し、匿名開始から20問のインタビュー、デモ候補とのアバター会話、
相性レポート、承諾または辞退、承諾後の架空プロフィール開示までを一気通貫で完成させる。

既存の `index.html`、`style.css`、`app.js`、ホーム画像、GIF、事業概要PDFはUIと体験の基準資料として
残す。新アプリはこれらへ機能を継ぎ足さず、画面構成、配色、文言、遷移、アニメーションを参照して
Reactコンポーネントとして再構築する。

採用する実装方針は「本番基盤を持つ縦切り」である。画面だけを先行移植せず、最初から回答、処理、
会話、評価、決定をデータベースへ保存する。一方、正式認証、実ユーザー探索、運営管理、実AIは
交換可能な境界の外へ置き、第1マイルストーンの完了を遅らせない。

## 2. システム構成

### 2.1 Webアプリ

- Next.js 16系、App Router、TypeScriptを使用する。
- ページと読み取り中心の表示はServer Componentsを基本とする。
- 入力、チャット演出、選択、進捗アニメーションなど、ブラウザ状態が必要な範囲だけを
  Client Componentsにする。
- 利用者操作による更新はServer Actionsを基本とし、外部サービスからのコールバック、ヘルス確認、
  明示的なHTTP契約が必要な処理だけRoute Handlersを使用する。
- サーバー専用モジュールで秘密値と管理権限を扱い、クライアントバンドルへの混入を防ぐ。

### 2.2 Supabase

Supabaseは次の責務を持つ。

- 匿名認証による端末単位の利用者ID発行
- Postgresによる回答、会話、評価、決定、通知の永続化
- Row Level Securityによる利用者単位のデータ分離
- 処理状態と通知のRealtime更新
- 将来のメールOTP等の正式認証へのID移行
- 必要になった場合の画像等のStorage管理

匿名認証は利用者にログイン操作を見せず、自動で開始する。正式認証を追加するときは、ドメイン上の
`UserIdentity` 境界を差し替え、回答やマッチングが参照する所有者IDの意味を維持する。

### 2.3 AIプロバイダー

AI処理はアプリから直接モデル固有APIを呼ばず、次の共通契約を介す。

```text
InterviewAnswers
  -> AvatarProfileGenerator
  -> AvatarConversationGenerator
  -> CompatibilityEvaluator
  -> Conversation + FiveAxisReport
```

第1マイルストーンは `MockAiProvider` を標準とする。回答内容を少なくとも3箇所へ反映し、同じ入力と
同じデモ候補からは再現可能な会話と評価を返す。次段階で `BedrockAiProvider` を追加しても、画面、
データモデル、状態遷移を変更しない。

BedrockはNext.jsのNode.jsサーバーからのみ東京リージョンへ呼び出す。IAMロールを使用し、権限を
対象モデルの推論操作へ限定する。全呼び出しで最大出力トークンを明示する。プロンプト、応答、
CloudWatchログへ個人情報を残さない。初期版は実名等を収集しないが、回答全文もログ出力しない。

## 3. ドメイン境界

| 領域 | 責務 | 主な依存先 |
|---|---|---|
| `identity` | 匿名セッション開始、現在利用者の解決、将来の正式認証移行 | Supabase Auth |
| `interview` | 20問の定義、回答検証、保存、進捗、修正可否 | Postgres |
| `avatar-profile` | 回答から非識別のアバター要約を作る | AI Provider |
| `matching` | デモ候補の一意割当と処理状態管理 | Postgres |
| `avatar-conversation` | アバター会話の生成と発言順序の確定 | AI Provider |
| `compatibility` | 5軸評価、説明、引用根拠の確定 | AI Provider |
| `decision` | 承諾・辞退の一度限りの確定と開示条件判定 | Postgres |
| `notifications` | 処理完了通知、既読管理、ホーム表示 | Postgres / Realtime |
| `support` | プライバシー、FAQ、設定、リセット | Postgres |

各領域は公開する型とユースケース関数だけを通じて利用し、UIがテーブル構造やモデル固有レスポンスへ
直接依存しないようにする。

## 4. データモデル

初期テーブルは以下を基本とする。具体的な列、制約、インデックスは実装計画で確定する。

| テーブル | 内容 | 重要制約 |
|---|---|---|
| `profiles` | 匿名利用者のアプリ状態 | `id = auth.uid()` |
| `interview_questions` | 20問の質問マスター | 安定した質問キー、表示順の一意性 |
| `interview_answers` | 質問ごとの回答 | 利用者と質問の組で一意 |
| `avatar_profiles` | 回答から作る非識別要約 | 利用者ごとに現行版1件 |
| `demo_candidates` | 架空候補の匿名会話用情報 | 実在人物情報を禁止 |
| `candidate_reveals` | 承諾後のみ返す架空の名前・所属・紹介 | ブラウザから直接SELECT不可 |
| `match_runs` | 候補割当、処理状態、失敗分類 | 利用者ごとの初期版マッチは1件 |
| `conversation_messages` | 順序付きアバター会話 | マッチと連番の組で一意 |
| `compatibility_reports` | 総合要約と公開可能状態 | 会話と5軸が揃うまで非公開 |
| `compatibility_dimensions` | 5軸のスコア、説明、引用参照 | 軸ごとに1件、0〜100 |
| `decisions` | 承諾または辞退 | マッチごとに1件、確定後変更不可 |
| `notifications` | アプリ内通知と既読状態 | 利用者所有 |

利用者所有テーブルはすべて `owner_id` を持ち、`auth.uid() = owner_id` を基本とするRLSを適用する。
候補開示情報は承諾済みかをサーバー側のデータベース関数で判定して返す。service roleキーは
ブラウザへ渡さない。

会話発言と5軸評価は同一トランザクションで公開可能状態へ移す。生成途中の部分データを画面へ
公開しない。重複実行は冪等性キーで同一処理へ収束させる。

## 5. ユーザーフロー

```text
開始
  -> 匿名セッション自動作成
  -> AIインタビュー（固定20問）
  -> アバター要約確認
  -> デモ候補を一意に割当
  -> queued -> processing
  -> 会話ログと5軸評価を同時確定
  -> completed + アプリ内通知
  -> 会話ログ・相性レポート
  -> 承諾確認 --------> 承諾確定 -> 架空プロフィール開示
  -> 辞退確認 --------> 辞退確定 -> 非開示の完了画面
```

質問本文、形式、選択肢はSpec Kit仕様書の `Interview Question Set` を単一の正とする。初期版は固定20問
（選択式15問、自由記述5問）で、標準所要時間を10〜15分とする。将来は基本20問に最大10問のAI深掘り
を加えるが、第1マイルストーンには含めない。

回答は1件ずつ保存する。保存中は同じ質問の多重送信を抑止し、失敗時は入力値を端末へ一時保持する。
マッチング開始前は過去回答を修正でき、要約を再生成する。開始後は評価との不整合を避けるため
回答をロックし、変更したい場合は現在のデモをリセットする。

## 6. UI設計

### 6.1 基本方針

- 既存デモに忠実なワインレッド、淡いピンク、白を基調とする。
- 既存のホーム画像と同じく、ヒーロー、現在の状況、進捗、お知らせ、4つのメニュー、匿名性バナー、
  下部ナビゲーションを基本構成とする。
- 「PoC忠実進化」の外観を採用しつつ、「タスク中心」の考え方を補助的に取り入れ、現在必要な主操作を
  カード内で最も目立たせる。
- スマートフォンを主対象にし、PCではスマートフォン相当の表示領域を中央に置く。
- 既存GIFの画面順、チャットの吹き出し、進捗バー、通知、レポートバー、承諾時のローディングと
  完了演出を再現する。

### 6.2 画面一覧

1. 体験開始
2. AIインタビュー（1画面1問）
3. インタビュー完了・アバター要約
4. ホーム
5. アバター会話中
6. お知らせ一覧
7. 会話ログ
8. 相性レポート
9. 承諾・辞退確認
10. 承諾後プロフィール開示
11. 辞退完了
12. マイページ
13. プライバシー
14. FAQ
15. 設定・デモリセット

### 6.3 アクセシビリティ

ネイティブ要素を優先し、すべての主要操作をキーボードで利用可能にする。フォーカスを可視化し、
本文と操作要素はWCAG AA相当のコントラストを確保する。状態は色だけで伝えない。ダイアログでは
フォーカスを管理し、スクリーンリーダーへ題名と結果を通知する。`prefers-reduced-motion` では移動や
バーの伸長を即時表示へ置き換える。

## 7. エラー処理と復旧

| 失敗 | 利用者への動作 | データの扱い |
|---|---|---|
| 匿名開始失敗 | 開始画面で再試行を提示 | アプリデータを作成しない |
| 回答保存失敗 | 未保存表示と再送を提示 | 入力を端末へ一時保持 |
| 会話生成失敗 | 無限待機を止め再試行を提示 | 回答と候補割当を保持 |
| 会話生成タイムアウト | 失敗状態へ遷移 | 同じ冪等性キーで再実行可能 |
| 部分生成 | レポートを非公開のまま失敗表示 | 部分データを削除または非公開で置換 |
| 不正な直接遷移 | 正しい最新画面へ戻す | 保存状態を変更しない |
| 二重決定 | 最初の決定を表示 | 後続更新を拒否 |
| リセット失敗 | 再試行を提示 | トランザクションで全件削除を保証 |

エラーメッセージは技術名を出さず、保持されている内容と次にできる操作を伝える。ログは
`request_id`、`anonymous_user_id` の不可逆な相関値、処理種別、状態、失敗分類、経過時間を持つ。
質問回答、会話全文、秘密値、開示情報はログへ出さない。

## 8. テスト戦略

### 8.1 単体テスト

- 質問順序、15対5の形式内訳、入力制約
- 進捗計算、回答修正可否、画面ガード
- マッチング状態遷移と冪等性
- 5軸スコア範囲と「不一致の重大度」の表示方向
- AIプロバイダー契約とモックの再現性

### 8.2 データベース・セキュリティテスト

- 全利用者所有テーブルでRLSが有効
- 利用者Aが利用者Bの全対象行をSELECT、INSERT、UPDATE、DELETEできない
- 承諾前と辞退後に開示情報を取得できない
- 承諾確定後だけ対象マッチの開示情報を取得できる
- マッチごとの決定一意性と確定後変更不可
- リセットが対象利用者のデータだけを削除する

### 8.3 統合・E2Eテスト

- 匿名開始から20問完了まで
- 7問目終了後の再開と過去回答修正
- モック会話生成、通知、ログ、5軸レポート
- 承諾経路と辞退経路
- 通信失敗、処理失敗、タイムアウト、再試行
- 320px幅、代表的なスマートフォン幅、PC中央表示
- キーボード操作、フォーカス順、reduced-motion

### 8.4 視覚回帰

既存ホーム画像とGIFから主要状態の参照スクリーンショットを選び、新実装の同一状態と比較する。
色の完全一致だけで合否を決めず、必須要素、情報階層、余白、カード構成、主操作、画面順が一致する
ことをチェックリスト化する。意図した改善は差分理由を記録する。

## 9. 完了条件

- Spec Kit仕様のP1からP3までのユーザーストーリーが実装される。
- 匿名開始から承諾後開示までの主要フローが実データ保存付きで動作する。
- 固定20問を保存、再開、修正できる。
- モック会話と5軸レポートが利用者回答を少なくとも3箇所反映する。
- 他利用者データアクセスと承諾前開示が全自動テストで0件となる。
- 型検査、Lint、単体、統合、RLS、E2E、プロダクションビルドがすべて成功する。
- 既存デモとの主要画面比較が合格する。
- ローカル起動、Supabase設定、マイグレーション、モック／Bedrock切替をREADMEへ記載する。
